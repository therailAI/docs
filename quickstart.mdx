---
title: "Quickstart"
description: "Run The Rail locally, make your first API call, and govern your first action, in about five minutes."
---

You'll start The Rail on your machine, call the API, run a protected action through authorization and dispatch, and verify the evidence offline. You need Docker and the `rail` CLI. You don't need an account, a hosted endpoint, or payment credentials.

## 1. Install the CLI

<Tabs>
  <Tab title="macOS and Linux (Homebrew)">
    ```bash
    brew install therailai/tap/rail
    ```
  </Tab>
  <Tab title="Binary download">
    Download the archive for your platform from [Rail CLI releases](https://github.com/therailAI/rail-cli-releases/releases), check it against `checksums.txt`, and put `rail` on your `PATH`.
  </Tab>
</Tabs>

```bash
rail version
```

## 2. Start the sandbox

Create a project and start The Rail on your machine:

```bash
mkdir acme-pay && cd acme-pay
rail init
rail sandbox up
```

`rail init` writes `rail.yaml`, which declares one action (`procurement.purchase_order.create`) with an approval threshold, plus an example effect script. `rail sandbox up` starts the sandbox, enrolls the project, saves a profile, and grants your project's agent authority within the declared limits. See [the local sandbox](/get-started/sandbox) for what runs and how to manage it.

## 3. Make your first call

```bash
curl --cacert "$(rail sandbox ca)" https://localhost:8443/v1/context \
  --header "Authorization: Bearer $(rail sandbox token)"
```

The response identifies who you are to The Rail: tenant, principal, OAuth subject, scopes, and projects. The Rail derives all of this from the token; there is no tenant header to set.

```json
{
  "api_version": "v1",
  "tenant_id": "ten_dev00000000000000001",
  "principal_id": "pri_7329ec4c9f71a6851bbb92e088fc4c49",
  "project_ids": ["prj_dev00000000000000001"],
  "scopes": ["authority:read", "authority:write", "platform:read", "..."],
  "oauth_subject": "1526b49e-ef4f-45e3-a6b5-289cebe40d10"
}
```

Your IDs differ. This token belongs to the project's governor, which manages authority. It can't run actions itself.

## 4. Govern an action

Your agent places a purchase order. The effect command runs only if The Rail authorizes and dispatches it:

```bash
rail govern procurement.purchase_order.create \
  --input '{"supplier_id":"SUP-ACME","amount":"250.00"}' \
  -- ./examples/effect.sh
```

```text
...
execution   exe_a3aaf8f20e6c86f254fcabb94e2b81b7
journey     grt_9d771fefd7ada391eb104ba596f8fe2b
state       completed
authorized  rec_02416ee734e4970d5b84d92b2d37d099
dispatch    rec_81a1ab320a347d1765dccadfcb9d70c7
result      rec_ca91775a1ba5ed58460bd838cf783f18
verified    rec_3a72f023c60f0d509aba453518002882
```

The output is abridged. Each `rec_` line is a signed receipt: the authorization decision, the dispatch permit, the effect's signed result, and its verification. The example effect is simulated; nothing real happens.

Now ask for more than the policy allows without approval:

```bash
rail govern procurement.purchase_order.create --own-authority \
  --input '{"supplier_id":"SUP-ACME","amount":"12000.00"}' \
  -- ./examples/effect.sh
```

The execution stops at `awaiting_approval` with `APPROVAL_REQUIRED`, and the effect does not run. [Approvals and inspection](/cli/approvals-and-inspection) shows how an approver votes and how the same execution resumes.

<Note>A grant covers each resource and action once, and a plain `rail govern` uses the agent's newest active grant. After the approval call, that is the one-use grant `--own-authority` just issued for the held execution: a plain call now would spend it, and the held execution could no longer run once approved. While experimenting, pass `--own-authority` on every repeat. See [governed commands](/cli/govern).</Note>

## 5. Verify the evidence

Export the journey and verify it offline, the way a third party would:

```bash
rail journey export grt_9d771fefd7ada391eb104ba596f8fe2b
```

The export writes a bundle and its trust file under `.rail/journeys/`, then verifies them: signatures and inclusion proofs, the authority chain, non-expansion, and capability binding. Anyone with the bundle can repeat the check without access to your Rail. See [export and verify](/cli/evidence).
