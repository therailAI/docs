---
title: "The control model"
description: "Connect identity, authority, execution, evidence, and consequences."
---

An agent's ability to call a tool is different from its permission to produce a particular effect. Rail evaluates the latter at protected boundaries.

| Object or decision | Purpose |
| --- | --- |
| Principal | An enrolled person, agent, or service identity |
| Project | An authorized grouping of resources and work |
| Versioned definition | The action, schema, policy, or artifact version governing a request |
| Authority grant | Bounded permission issued under governing authority |
| Delegation | A narrower scope passed to another principal |
| Canonical action | A normalized intent, pinned to its definition |
| Execution | A governed attempt with a stable business-operation identity |
| Receipt | An immutable record of an assertion, decision, or outcome |
| Projection and effect decision | Scoped evaluation of evidence and permission for a named consequence |
| Realization and settlement | Value accounting and separately governed release |

## Follow a protected action

An agent submits an intent. Rail normalizes it, evaluates authority and policy, obtains approval if required, and selects only from eligible execution paths. Authority and prerequisites are checked again at the consequential boundary.

A runtime result is evidence to evaluate. It does not, by itself, establish completion, permit result release, or authorize payment. Each of those consequences can require a separate decision.

## Changes remain visible

Revocation changes future permission. It does not rewrite historical receipts. A changed model or artifact version can invalidate the applicability of earlier evidence without proving that the new version is unsafe.
