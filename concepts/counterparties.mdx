A **Counterparty** represents an external financial endpoint — a bank account, crypto wallet, or other payment destination that your customers send funds to or receive funds from. Before any withdrawal or payment can leave the Rail platform, the destination must exist as a verified counterparty on the customer's profile. This requirement exists to satisfy AML/CFT compliance obligations: Rail must know and verify the parties involved in every outbound transaction before funds are released.

## Why Counterparties Matter

When a customer wants to withdraw funds to their personal bank account or send crypto to an external wallet, you do not simply pass raw account numbers into the withdrawal API. Instead, you first register that destination as a **Counterparty**, allow it to pass compliance verification, and then reference the resulting `counterparty_id` when initiating withdrawals. This design:

- Enables pre-clearance of beneficiary details before funds move
- Reduces withdrawal latency (verification happens once, not per transaction)
- Creates an auditable record of all external financial relationships
- Satisfies FATF travel rule and similar regulatory requirements

<Note>
  Counterparties are scoped to a specific customer. A bank account registered for one customer cannot be referenced in a withdrawal for a different customer.
</Note>

## Counterparty Types

Rail supports four counterparty types to accommodate different external financial endpoints:

<CardGroup cols={2}>
  <Card title="BASIC" icon="circle-info">
    Minimal information required. Suitable for simple payment collection scenarios where full bank details are not needed. Use this type when you only need to collect funds from a counterparty.
  </Card>
  <Card title="FIAT_US" icon="building-columns">
    A US bank account identified by routing number and account number. Supports outbound ACH and wire (FEDWIRE) transfers. Required for any USD withdrawal to a domestic bank account.
  </Card>
  <Card title="CRYPTO" icon="ethereum">
    A blockchain wallet address. Supports outbound on-chain transfers for any supported crypto asset. You specify the asset type and the wallet address at registration time.
  </Card>
  <Card title="LINKED" icon="link">
    A bank account verified through a third-party open-banking provider such as **Plaid** or **MX**. Linked counterparties benefit from instant account verification and typically pass compliance checks faster than manually entered bank details.
  </Card>
</CardGroup>

## Compliance Verification Lifecycle

Every counterparty goes through an automated compliance review after registration. The lifecycle is linear:

```text
  POST /v1/counterparties
           │
           ▼
        PENDING  ──► (automated compliance review)
           │
           ▼
         ACTIVE  ──► (available for withdrawals and payments)
```

| Status | Description |
|---|---|
| `PENDING` | Counterparty has been registered and is under compliance review |
| `ACTIVE` | Counterparty has passed verification and can be used in transactions |
| `REJECTED` | Counterparty failed compliance checks; cannot be used for transactions |

<Warning>
  You cannot initiate a withdrawal to a counterparty that is in `PENDING` or `REJECTED` status. Poll the counterparty record or listen for the `counterparty.activated` webhook event before attempting a withdrawal.
</Warning>

<Tip>
  Use **LINKED** counterparties (via Plaid or MX) when you need the fastest path from registration to `ACTIVE`. Automated account verification significantly reduces the compliance review time compared to manually entered bank details.
</Tip>

## Registering a Counterparty

Use `POST /v1/counterparties` to register a new external financial endpoint for a customer. The required fields differ by counterparty type.

          "customer_id": "cust_01hq7z3xkfbp9rn2vwme4d5j6c",

## Retrieving a Counterparty

Use `GET /v1/counterparties/{counterparty_id}` to fetch a counterparty record at any time — for example, to poll its status while waiting for compliance verification to complete.

<CodeGroup>
  ```bash cURL
  curl --request GET \
    --url https://sandbox.layer2financial.com/api/v1/counterparties/{counterparty_id} \
    --header 'Authorization: Bearer YOUR_API_KEY'
  ```

  ```javascript Node.js
  const response = await fetch(
    `https://sandbox.layer2financial.com/api/v1/counterparties/${counterpartyId}`,
    {
      method: 'GET',
      headers: {
        'Authorization': `Bearer ${process.env.RAIL_API_KEY}`,
      },
    }
  );

  const counterparty = await response.json();
  console.log(counterparty.counterparty_id, counterparty.status);
  ```

  ```python Python
  import requests

  response = requests.get(
      f"https://sandbox.layer2financial.com/api/v1/counterparties/{counterparty_id}",
      headers={"Authorization": f"Bearer {api_key}"},
  )

  counterparty = response.json()
  print(counterparty["counterparty_id"], counterparty["status"])
  ```
</CodeGroup>

**Example response:**

```json
{
  "counterparty_id": "cp_01hr2k9mpvxq5nt7bwlf3g8c4e",
  "customer_id": "cust_01hq7z3xkfbp9rn2vwme4d5j6c",
  "type": "FIAT_US",
  "name": "Alice Johnson",
  "status": "ACTIVE",
  "created_at": "2024-03-15T13:00:00Z",
  "updated_at": "2024-03-15T13:02:45Z"
}
```

<Tip>
  Rather than polling, subscribe to the `counterparty.activated` webhook event to be notified the moment a counterparty transitions to `ACTIVE`. See [Webhook Events](/webhooks/events).
</Tip>

## Linking via Plaid or MX

For `LINKED` counterparties, your integration connects a customer's bank account through a third-party open-banking provider. The flow works as follows:

<Steps>
  <Step title="Initiate a Link Session">
    Call the Rail API to generate a link token for Plaid or MX. Return this token to your frontend.
  </Step>
  <Step title="Customer Authenticates">
    Your frontend launches the Plaid Link or MX Connect widget using the token. The customer logs in to their bank and selects the account to link.
  </Step>
  <Step title="Exchange the Token">
    After the customer completes the widget flow, exchange the provider's public token via the Rail API to finalize the linked counterparty. Rail handles the token exchange and account verification internally.
  </Step>
  <Step title="Counterparty Becomes ACTIVE">
    Because the account has been verified by the open-banking provider, the counterparty typically transitions to `ACTIVE` faster than manually entered bank details.
  </Step>
</Steps>

## Key Fields

<ResponseField name="counterparty_id" type="string" required>
  The unique Rail-assigned identifier for this counterparty. Pass this ID in withdrawal and payment requests.
</ResponseField>

<ResponseField name="customer_id" type="string" required>
  The customer this counterparty belongs to.
</ResponseField>

<ResponseField name="type" type="string" required>
  One of `BASIC`, `FIAT_US`, `CRYPTO`, or `LINKED`.
</ResponseField>

<ResponseField name="status" type="string" required>
  Current verification status: `PENDING`, `ACTIVE`, or `REJECTED`.
</ResponseField>

<ResponseField name="name" type="string">
  A human-readable label for the counterparty, such as the account holder's name or wallet alias.
</ResponseField>
