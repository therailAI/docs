---
title: "Idempotency and retries"
description: "Keep HTTP request recovery separate from business-effect identity."
---

Every customer `POST` and `PATCH` requires `Idempotency-Key`: 16–128 visible ASCII characters. Generate and persist a key before the first request. Reuse it only to recover that same request and payload.

| Mechanism | Responsibility |
| --- | --- |
| HTTP idempotency key | Recover the same API request within its response-cache scope |
| `operation_instance_id` | Identify the same business effect across execution submissions |
| Target/provider idempotency | Avoid repeating an effect in the external system |
| Authority reservation and fence | Control who may use bounded authority at the effect boundary |

The contract scopes HTTP idempotency to tenant, principal, method, and normalized path. Identical content replays the original response within the retention window. Changed canonical content returns `409`; a pending duplicate can return `409` with `Retry-After`.

The contract specifies at least 24 hours of response-cache retention. Business-operation uniqueness and unresolved-effect restrictions outlive that cache. Do not interpret expiry as permission to repeat an effect.

## Do not blindly retry

The SDKs perform one request and do not automatically retry mutations. Handle uncertainty by inspecting the original operation and reconciling it. A new HTTP key or business-operation ID cannot bypass a known unresolved effect.

For a genuinely new authorized invocation, create a new operation identity and fresh request keys. Do not reuse a key for a fresh policy decision.

## Optimistic concurrency

When required, send the exact strong ETag from the latest resource read in `If-Match`. Missing preconditions return `428`; stale preconditions return `412`. Re-read and review the current state before deciding whether a new mutation is appropriate.
