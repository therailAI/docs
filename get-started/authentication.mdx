---
title: "Authenticate to Rail"
description: "Use OAuth, enrolled identity, and scoped object access."
---

Customer API calls use an OAuth 2.0 access token:

```http
Authorization: Bearer YOUR_ACCESS_TOKEN
Accept: application/json
```

The identity provider and token endpoint are deployment-specific. Obtain access tokens using your operator's configured flow; the documentation does not supply a universal token URL or client secret.

## Workloads and people

Use client credentials for enrolled workloads. Interactive approval votes require a human identity using the deployment's Authorization Code flow with PKCE S256 and any policy-required step-up. A machine token cannot cast a human vote.

## Tenant and project access

Rail derives tenant and principal identity from the validated issuer, audience, subject, and active enrollment. A caller-supplied tenant field or header cannot select another tenant. `project_id` and every referenced object must be authorized independently.

Start with [`GET /v1/context`](/api-reference/endpoints/get-context). Confirm your principal, scopes, and project IDs before sending mutations.

## Scope is necessary, but not sufficient

The reference page for each operation lists its required OAuth scopes. For example, execution submission requires `execution:write`. Current authority, policy, object access, and evidence conditions still control whether the action may proceed.

## Capabilities and sender binding

A Rail capability is an action credential, separate from the OAuth access token. When required by the grant or delegation policy, supply it in `Rail-Capability` on execution submission. The capability binds to the action, operation identity, audience, expiry, and authenticated sender.

The customer contract's OAuth security scheme does not remove a capability's mTLS sender-binding requirement. Use the certificate-bound token and transport profile supplied for that environment; a plain bearer-only curl example is not sufficient for a capability-bound execution.

Runtime and internal-service ingress use separate credentials and transport boundaries. They are not part of this public customer reference.

See [grants and delegation](/guides/grants-and-delegation) and [request conventions](/api-reference/overview).
