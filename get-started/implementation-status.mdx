The documentation was reconciled with repository source on **October 3, 2026**, for release **0.2.0**. The audit compared the customer contract, registered service handlers, both SDK operation catalogs, authentication, selected implementation restrictions, and the developer tools.

## Customer API coverage

All **127 customer operations** have registered handlers across ten services. Their paths, request schemas, and successful-response schemas agree with both SDK catalogs and the published **0.1.1** customer contract.

This is source coverage, not a claim that every semantic branch, provider integration, or production deployment has passed end-to-end qualification. Endpoint-specific implementation notes identify reviewed restrictions; missing dependencies and governance profiles fail closed.

| Service | Customer operations | Address supplied by your operator |

| `platform` | 10 | Context, projects, principals, and objects |
| `execution` | 15 | Actions, executions, approvals, and operations |
| `registry` | 12 | Assets, versions, and process cases |
| `authority` | 13 | Grants, delegations, capabilities, and reservations |
| `evidence` | 15 | Receipts, verification, and effect decisions |

The six product groups organize the API; they are not six network services. Reference deployments expose service-specific addresses. A single base URL works across products when a gateway routes those paths: the [local sandbox](/get-started/sandbox) includes one at `https://localhost:8443`, and an operator can provide one. Each endpoint page names its owning service.

## Developer tools in 0.2.0

Every Rail developer tool shares one version number. Release 0.2.0 targets customer contract 0.1.1.

| Tool | Package | What it provides |
| --- | --- | --- |
| Rail CLI | `rail` (Homebrew `therailai/tap/rail`, or a release binary) | Project setup, the local sandbox, profiles, governed commands, authority and approval administration, journey export, and offline verification |
| Local sandbox | `ghcr.io/therailai/rail-sandbox:0.2` (started by `rail sandbox up`) | The full Rail in one container, with a gateway for every customer path |
| TypeScript SDK | `@therailai/sdk` | Typed customer client, pagination, operation polling, typed errors, the governed helper, runtime workers |
| Python SDK | `therail-sdk` (import `rail_sdk`) | The same set for Python |
| MCP proxy | `@therailai/mcp` | Governs an MCP server's tool calls |

The SDKs, CLI and MCP proxy are licensed under The Rail Developer Tools License, included with each package. It covers using them to build and run applications that work with The Rail.

## Implementation restrictions that affect integration

- **Identity:** creating a principal record does not configure an active OIDC enrollment. Token issuer, audience, subject mapping, effective scopes, and project access are operator-managed. Human approval requires a human enrollment; login and step-up flows belong to the configured identity provider.
- **Reconciliation:** `evidence_review` and `compensation_review` are implemented. The contract's target-status and idempotency-state query reasons currently return an unavailable response. Compensation permission does not execute a compensating effect.
- **Approvals:** execution supports its enrolled approval workflow. Grant/delegation issuance, registry operations, and routing operations do not automatically gain that workflow when their policy requests an unsupported obligation.
- **Results:** completion and result release are separate gates. The result endpoint releases an admitted assertion; retrieve application output through the object/artifact flow when applicable.
- **Webhooks:** HTTPS destinations require operator hostname approval and ownership verification. The Rail has its own signing format; no Svix backend was established by this audit.
- **Settlement:** a customer request is not provider confirmation. Qualify the custody adapter, funding, and outcome reconciliation for your environment.

## Verification boundaries

The audit checks source registration, contract/schema agreement, and SDK compatibility. Each release also runs the documentation's quickstart and SDK examples against the sandbox image it ships. No authenticated production API or real payment provider was exercised. Recorded workflows and the local sandbox use test, stub, or simulated integrations; see their limitations.

Use [environment setup](/get-started/environment) for connection prerequisites and the endpoint's implementation notes for restrictions before integrating.
