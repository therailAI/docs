description: "Consume change notifications without treating them as authority."

Rail provides a durable events feed and signed webhook subscriptions. Notifications contain resource references and minimal state. Fetch the resource under current authorization before relying on its current state.

## Create and activate a subscription

First have your operator approve the destination hostname in the deployment's webhook allowlist. The service rejects an unapproved hostname with `422 webhook_destination_not_allowed`. The outbound sender also enforces public-address checks and disallows redirects; a valid HTTPS URL alone is insufficient.

Create a subscription for that HTTPS destination and selected event types. It remains `pending_verification` until the ownership challenge succeeds. Store the generated signing secret securely when returned; it is shown once. An expired challenge leaves the subscription disabled; create a new subscription to obtain a new challenge. Changing state or rotating the secret cannot bypass ownership verification.

For a challenge, verify the signature using `challenge_id` in the signing input. Return HTTP 200 with the exact challenge in `{"challenge":"received value"}` within ten seconds. Challenges expire after five minutes. Failed or mismatched challenges do not activate the subscription.

## Verify raw bytes

Headers include `Rail-Webhook-Timestamp`, `Rail-Webhook-Key-Version`, and `Rail-Webhook-Signature`.

```text
signing input = ASCII(timestamp) + "." + UTF8(event.id) + "." + raw_request_body_bytes
signature = "v1=" + lowercase_hex(HMAC-SHA256(decoded_secret, signing_input))
```

Decode the supplied unpadded base64url secret to its 32 bytes before use. Preserve the raw body. Enforce strict body/JSON bounds, reject duplicate JSON keys, validate the key version, and allow no more than 300 seconds of clock skew. Parse only enough to retrieve the ID before verification; trust no event data yet.

The SDK verification helper checks the HMAC and timestamp. Your receiver still owns strict parsing, key-version selection, rotation handling, and durable deduplication.

## Acknowledge only after persistence

After verification, atomically persist the event ID and enqueue work before returning 2xx. A valid duplicate can return 204 without repeating the work. Keep deduplication at least as long as the configured feed/manual replay horizon; business-effect idempotency remains separate.

## Delivery and rotation

Delivery is at least once, with no ordering guarantee. The contract defines retries for up to 72 hours, a maximum one-hour delay, and a 24-hour secret-rotation overlap. The timestamp is fresh on each attempt; the event ID remains stable.

These are contract policies to confirm for your deployment. Replay redelivers a notification; it does not re-execute the business action or payment. Polling the feed is an alternative to a webhook receiver.
