## Two SDK layers

- **`RailClient`** makes customer API calls with a bearer token: reads, authority management, evidence, assets, settlement. It validates requests and responses against the contract.
- **The governed helper** (`Rail.fromProfile` in TypeScript, `Rail.from_profile` in Python) runs one protected effect through the whole lifecycle: action, capability, authorization, dispatch, your effect, the signed result, and verification. It needs the agent's and worker's certificate-bound credentials, which a profile supplies; a bearer token alone is not enough.

Start a governed call with the [TypeScript](/sdks/governed-typescript) or [Python](/sdks/governed-python) guide.

## Customer API namespaces

Both clients expose the same operation catalog. Product namespaces group operations without changing schemas or authority requirements.

| Namespace | Product |
| --- | --- |
| `execution` | Governed Execution |
| `authority` | Agent Authority |
| `evidence` | Evidence & Verification |
| `assets` | Assets & Lifecycle |
| `lineage` | Lineage & Rights |
| `settlement` | Settlement |

Shared and advanced operations are available through the generic `call` method with the contract's operation ID.

## Client behavior

Both clients:

- validate request and response shape against the contract, and reject a response that doesn't match;
- require an explicit idempotency key on every mutation, and provide `newIdempotencyKey()` / `new_idempotency_key()`;
- page through lists (`paginate`) and wait for asynchronous operations (`waitForOperation` / `wait_for_operation`);
- raise a typed error per problem status, all subclasses of `RailError`;
- retry only `GET` requests answered `429` or `503` with `Retry-After`. **Mutations are never retried automatically.**

A client uses one base URL. The sandbox gateway routes every customer path; in an operator environment without a gateway, use one client per service address.
