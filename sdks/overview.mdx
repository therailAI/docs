## Two SDK layers

Use `RailClient` for customer API calls. Use `Rail.fromProfile` in TypeScript or `Rail.from_profile` in Python to coordinate a protected effect through an enrolled worker. The latter requires runtime configuration and role-specific credentials beyond the customer HTTP API.

Start a governed call with the [TypeScript example](/sdks/governed-typescript) or [Python example](/sdks/governed-python).

## Customer API namespaces

The TypeScript and Python clients expose the same customer operation catalog. Product namespaces group operations without changing request schemas, response schemas, or authority requirements.

| Namespace | Product |
| --- | --- |
| `execution` | Governed Execution |
| `authority` | Agent Authority |
| `evidence` | Evidence & Verification |
| `assets` | Assets & Lifecycle |
| `lineage` | Lineage & Rights |
| `settlement` | Settlement |

Shared and advanced operations are available through the generic `call` method. TypeScript uses camelCase operation names; Python product methods use snake_case. The generic Python `call` accepts the contract's camelCase operation ID.

## Distribution status

These guides describe TypeScript SDK `0.2.0-dev.0` and Python SDK `0.2.0.dev0` against customer contract 0.1.1. The inspected TypeScript package is private. Obtain a versioned source checkout or distribution from your Rail operator; do not assume `npm install @rail/sdk` or `pip install rail-sdk` resolves to a supported public release. Obtain the matching CLI binary or workspace from the same operator.

The examples use Node.js 22 or Python 3.12+, respectively. Supply environment credentials separately.

## Client behavior

Both clients validate request and successful-response shape and require explicit idempotency keys for mutations. They perform one request without automatic mutation retries. They return data and response metadata; the metadata is useful for ETags and asynchronous resource locations.
