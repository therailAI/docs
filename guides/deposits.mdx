Deposits on Rail represent inbound funds arriving from outside the platform into a customer's deposit account. Unlike withdrawals or transfers, you do not initiate a deposit directly — funds arrive automatically when a counterparty sends them via a supported payment rail. Rail reconciles the incoming payment, credits the account, and notifies you via webhook or a queryable transaction record. Your responsibility is to provide the correct deposit instructions to your customers and to monitor for settlement.

## How deposits work

When a customer's counterparty initiates a bank transfer or blockchain transaction to the routing details associated with a Rail deposit account, the following happens automatically:

1. Rail's banking or blockchain infrastructure receives the incoming payment.
2. The funds are matched to the correct deposit account using the routing number, account number, or on-chain address.
3. The deposit is reconciled and the account balance is updated.
4. A `account.deposit.completed` webhook event is emitted.
5. The transaction appears in the account's transaction history.

<Note>
  Settlement timelines vary by rail. ACH transfers may take 1–2 business days, while Fedwire and SWIFT same-day transfers typically settle within hours. Crypto deposits confirm according to the blockchain's block time and required confirmations.
</Note>

## Supported deposit rails

Rail supports the following inbound payment methods. Each requires a different set of routing details, all returned from the deposit instructions endpoint.

<CardGroup cols={2}>
  <Card title="ACH" icon="building-columns">
    Automated Clearing House transfers. Ideal for recurring US domestic payments. Requires routing number and account number.
  </Card>
  <Card title="Fedwire" icon="bolt">
    US domestic wire transfers. Same-day settlement for high-value or time-sensitive transfers. Requires ABA routing number and account number.
  </Card>
  <Card title="SWIFT" icon="globe">
    International wire transfers. Supports cross-border payments in multiple currencies. Requires SWIFT/BIC code, IBAN or account number, and correspondent bank details.
  </Card>
  <Card title="Crypto" icon="link">
    On-chain deposits via blockchain address. Supported networks include Ethereum, Bitcoin, and others depending on your product configuration.
  </Card>
</CardGroup>

## Retrieving deposit instructions

Before a customer can fund an account, you must retrieve the deposit instructions for that account and present them through your product interface. Instructions are stable and can be cached.

```bash
curl -X GET 'https://sandbox.layer2financial.com/api/v1/accounts/deposits/CUST001.USD.001/deposit-instructions' \
  --header 'Authorization: Bearer {AUTH_TOKEN}'
```

**Response:**

```json
{
  "data": {
    "account_id": "CUST001.USD.001",
    "rails": {
      "ach": {
        "routing_number": "021000021",
        "account_number": "9876543210",
        "account_type": "CHECKING"
      },
      "fedwire": {
        "routing_number": "021000021",
        "account_number": "9876543210",
        "bank_name": "Rail Partner Bank",
        "bank_address": "1 Finance St, New York, NY 10001"
      },
      "swift": {
        "swift_code": "RLBNUS33",
        "account_number": "9876543210",
        "bank_name": "Rail Partner Bank",
        "bank_address": "1 Finance St, New York, NY 10001"
      },
      "crypto": {
        "ethereum": {
          "address": "0xAbC1234567890DeF1234567890abcdef12345678",
          "network": "ETHEREUM_MAINNET"
        }
      }
    }
  }
}
```

<Tip>
  Display all applicable rails to your customer in a clean, copyable format. Many bank portals require each field separately (routing number, account number, bank address), so break them out in your UI rather than presenting a single string.
</Tip>

## Monitoring deposits

You have two options for detecting when deposits arrive: webhooks (recommended) and polling.

<Tabs>
  <Tab title="Webhooks (recommended)">
    Subscribe to the `account.deposit.completed` event to receive a real-time notification whenever a deposit settles. This eliminates the need to poll and ensures your system reacts to inbound funds as quickly as possible.

    **Example webhook payload:**

    ```json
    {
      "event": "account.deposit.completed",
      "data": {
        "account_id": "CUST001.USD.001",
        "transaction_id": "txn_dep_789",
        "amount": 2500.00,
        "asset_type": "FIAT_USD",
        "rail": "ACH",
        "settled_at": "2024-06-15T14:32:00Z"
      }
    }
    ```

    See [Webhooks Overview](/webhooks/overview) for endpoint configuration, signature verification, and retry policies.

    <Note>
      Rail retries unacknowledged webhook deliveries with exponential backoff. Always return a `200 OK` immediately upon receipt and process the event asynchronously to avoid missed notifications.
    </Note>
  </Tab>

  <Tab title="Polling">
    If webhooks are not feasible for your integration, you can poll the transactions endpoint to check for new deposits. This approach is suitable for low-frequency reconciliation jobs but is not recommended for real-time use cases.

    ```bash
    curl -X GET 'https://sandbox.layer2financial.com/api/v1/accounts/deposits/CUST001.USD.001/transactions' \
      --header 'Authorization: Bearer {AUTH_TOKEN}'
    ```

    **Response:**

    ```json
    {
      "data": [
        {
          "id": "txn_dep_789",
          "type": "DEPOSIT",
          "amount": 2500.00,
          "asset_type": "FIAT_USD",
          "rail": "ACH",
          "status": "COMPLETED",
          "created_at": "2024-06-15T12:00:00Z",
          "settled_at": "2024-06-15T14:32:00Z"
        }
      ],
      "pagination": {
        "next_cursor": "cursor_abc",
        "has_more": false
      }
    }
    ```

    Use the `next_cursor` value from the pagination object on subsequent requests to page through large transaction sets without re-fetching records you've already processed. See the [Pagination guide](/api-reference/pagination) for details.
  </Tab>
</Tabs>

## Transaction fields reference

<ResponseField name="id" type="string">
  Unique transaction identifier (e.g. `txn_dep_789`).
</ResponseField>

<ResponseField name="type" type="string">
  Always `DEPOSIT` for inbound transactions.
</ResponseField>

<ResponseField name="amount" type="number">
  The amount credited to the account after any fees.
</ResponseField>

<ResponseField name="asset_type" type="string">
  The asset type credited (e.g. `FIAT_USD`, `ETHEREUM_MAINNET_ETH`).
</ResponseField>

<ResponseField name="rail" type="string">
  The payment rail used. One of `ACH`, `FEDWIRE`, `SWIFT`, or a blockchain identifier such as `ETHEREUM_MAINNET`.
</ResponseField>

<ResponseField name="status" type="string">
  Transaction status. `PENDING` while awaiting settlement; `COMPLETED` once funds are available.
</ResponseField>

<ResponseField name="settled_at" type="string">
  ISO 8601 timestamp of when the deposit settled and became available.
</ResponseField>

## Best practices

<CardGroup cols={2}>
  <Card title="Validate memo / reference fields" icon="tag">
    For SWIFT and Fedwire deposits, instruct senders to include a unique reference or memo. This accelerates matching and reduces manual reconciliation if a payment arrives without complete details.
  </Card>
  <Card title="Handle pending state" icon="clock">
    Show customers a "pending" badge for transactions in `PENDING` status. Do not unlock downstream features (e.g. trading or withdrawals) until the deposit status is `COMPLETED`.
  </Card>
  <Card title="Idempotent event processing" icon="shield-check">
    Your webhook handler may receive the same event more than once under retry scenarios. Use `transaction_id` as an idempotency key in your database to prevent double-crediting.
  </Card>
  <Card title="Test each rail in sandbox" icon="flask">
    Rail's [Sandbox environment](/get-started/sandbox) lets you simulate ACH, Fedwire, and crypto deposits to validate your integration before going live.
  </Card>
</CardGroup>
