Withdrawals move funds from a customer's Rail deposit account to an external destination — a bank account, wire recipient, or crypto address — represented on Rail as a counterparty. Because withdrawals leave the platform, they are subject to compliance checks including real-time AML screening and, for larger amounts, automated Requests for Information (Auto-RFI). This guide walks you through setting up a counterparty, initiating a withdrawal, handling any compliance holds, and monitoring the transaction through to completion.

## Withdrawal status lifecycle

```text
REQUESTED → PENDING → PROCESSING → COMPLETED
                                  ↘ FAILED
```

| Status | Meaning |
|---|---|
| `REQUESTED` | Withdrawal created; pre-flight validation in progress |
| `PENDING` | Accepted by the compliance engine; queued for processing |
| `PROCESSING` | Submitted to the payment rail; funds are in transit |
| `COMPLETED` | Funds have left the platform and been sent to the counterparty |
| `FAILED` | Withdrawal could not be processed; see the `failure_reason` field |

<Note>
  A `PROCESSING` withdrawal cannot be cancelled once it has reached the payment processor. Monitor status proactively and surface it to your customers in real time.
</Note>

## Step-by-step: initiating a withdrawal

<Steps>
  <Step title="Create an ACTIVE counterparty">
    Every withdrawal requires a pre-registered counterparty — a named, verified external recipient. Create a counterparty with `ENHANCED` type (required for withdrawals) and wait for its status to become `ACTIVE` before initiating any withdrawals to it.

    ```bash
    curl -X POST 'https://sandbox.layer2financial.com/api/v1/counterparties' \
      --header 'Authorization: Bearer {AUTH_TOKEN}' \
      --header 'Content-Type: application/json' \
      --data '{
        "customer_id": "CUST001",
        "counterparty_type": "ENHANCED",
        "profile": {
          "profile_type": "INDIVIDUAL",
          "name": "Alice Johnson",
          "address": {
            "street_line_1": "789 Oak Ave",
            "city": "Chicago",
            "state": "IL",
            "postal_code": "60601",
            "country_code": "US"
          },
          "relationship_to_customer": "SELF"
        },
        "bank_details": {
          "routing_number": "071000013",
          "account_number": "1234567890",
          "account_type": "CHECKING",
          "bank_name": "Example Bank"
        }
      }'
    ```

    **Response:**

    ```json
    {
      "data": {
        "id": "cp_xyz789",
        "status": "ACTIVE"
      }
    }
    ```

    <Warning>
      Withdrawals submitted with a counterparty that is not in `ACTIVE` status will be rejected. Check the counterparty status before each withdrawal if your workflow allows for counterparty updates.
    </Warning>
  </Step>

  <Step title="Initiate the withdrawal">
    With an `ACTIVE` counterparty, call `POST /v1/withdrawals` to create the withdrawal request. Provide the source account, the destination counterparty, the amount, asset type, and an optional human-readable description.

    ```bash
    curl -X POST 'https://sandbox.layer2financial.com/api/v1/withdrawals' \
      --header 'Authorization: Bearer {AUTH_TOKEN}' \
      --header 'Content-Type: application/json' \
      --data '{
        "source_account_id": "CUST001.USD.001",
        "destination_counterparty_id": "cp_xyz789",
        "amount": 1000.00,
        "asset_type": "FIAT_USD",
        "description": "Monthly payout"
      }'
    ```

    **Response:**

    ```json
    {
      "data": {
        "id": "wdl_lmn321",
        "status": "REQUESTED",
        "source_account_id": "CUST001.USD.001",
        "destination_counterparty_id": "cp_xyz789",
        "amount": 1000.00,
        "asset_type": "FIAT_USD"
      }
    }
    ```

    Store the withdrawal `id` for status tracking.
  </Step>

  <Step title="Handle Auto-RFI (if triggered)">
    Withdrawals above certain thresholds — or those that match compliance risk signals — automatically trigger an Auto-RFI (Request for Information). When this occurs, the withdrawal is held in `PENDING` status and you will receive a `withdrawal.rfi_required` webhook event.

    Check the withdrawal status for RFI details:

    ```bash
    curl -X GET 'https://sandbox.layer2financial.com/api/v1/withdrawals/wdl_lmn321/status' \
      --header 'Authorization: Bearer {AUTH_TOKEN}'
    ```

    **Response (RFI triggered):**

    ```json
    {
      "data": {
        "id": "wdl_lmn321",
        "status": "PENDING",
        "rfi": {
          "required": true,
          "reason": "Transaction exceeds reporting threshold",
          "documents_required": ["SOURCE_OF_FUNDS"]
        }
      }
    }
    ```

    Upload the required document to resolve the RFI:

    ```bash
    curl -X POST 'https://sandbox.layer2financial.com/api/v1/withdrawals/wdl_lmn321/documents' \
      --header 'Authorization: Bearer {AUTH_TOKEN}' \
      --form 'document_type="SOURCE_OF_FUNDS"' \
      --form 'file=@"/path/to/bank_statement.pdf"'
    ```

    Once the document is reviewed and approved, the withdrawal will resume processing automatically.

    <Note>
      Auto-RFI thresholds are set at the platform configuration level. Contact Rail support to understand the thresholds applicable to your integration.
    </Note>
  </Step>

  <Step title="Monitor withdrawal status">
    Poll the status endpoint or subscribe to `withdrawal.completed` and `withdrawal.failed` webhook events to know when a withdrawal has been finalized.

    ```bash
    curl -X GET 'https://sandbox.layer2financial.com/api/v1/withdrawals/wdl_lmn321/status' \
      --header 'Authorization: Bearer {AUTH_TOKEN}'
    ```

    **Response (completed):**

    ```json
    {
      "data": {
        "id": "wdl_lmn321",
        "status": "COMPLETED",
        "completed_at": "2024-06-15T16:45:00Z"
      }
    }
    ```
  </Step>
</Steps>

## Auto-RFI explained

Auto-RFI is Rail's automated mechanism for requesting additional information from customers when a withdrawal triggers a compliance review. It is distinct from a manual compliance hold — the system raises it automatically based on configurable rules, and it can be resolved without human intervention on Rail's side once the required documents are uploaded.

Common triggers include:

- Withdrawal amount exceeds a reporting threshold (e.g. $10,000 CTR threshold in the US)
- Unusual transaction velocity or destination patterns
- First-time withdrawal to a new counterparty above a configured limit

<Warning>
  Do not notify the customer that their transaction has been flagged for compliance review in a way that could be interpreted as a "tipping off" disclosure. Consult your legal counsel on appropriate customer-facing messaging for held transactions.
</Warning>

## Withdrawal request fields reference

<ParamField body="source_account_id" type="string" required>
  The ID of the Rail deposit account to debit. Must be in `OPEN` status with sufficient `available_balance`.
</ParamField>

<ParamField body="destination_counterparty_id" type="string" required>
  The ID of the target counterparty. Must be in `ACTIVE` status.
</ParamField>

<ParamField body="amount" type="number" required>
  The amount to withdraw, expressed as a decimal. Must not exceed the account's `available_balance`.
</ParamField>

<ParamField body="asset_type" type="string" required>
  The asset type to withdraw (e.g. `FIAT_USD`, `ETHEREUM_MAINNET_ETH`). Must match the source account's `asset_type_id`.
</ParamField>

<ParamField body="description" type="string">
  Optional human-readable description. Appears in transaction records and may be included as a payment reference on the outbound rail.
</ParamField>

## Best practices

<CardGroup cols={2}>
  <Card title="Pre-register counterparties" icon="address-book">
    Create and verify counterparties ahead of time rather than at withdrawal initiation. This avoids user-facing latency during the payout flow.
  </Card>
  <Card title="Surface status to customers" icon="eye">
    Display withdrawal status in your product UI and send customers a notification when a withdrawal completes or fails. Avoid leaving customers uncertain about outbound funds.
  </Card>
  <Card title="Handle FAILED gracefully" icon="triangle-exclamation">
    When a withdrawal fails, check the `failure_reason` field and provide actionable guidance. Common reasons include insufficient balance, invalid counterparty details, and compliance rejection.
  </Card>
  <Card title="Use idempotency keys" icon="key">
    Pass an `Idempotency-Key` header on every withdrawal request to prevent duplicate submissions from retries. See the [Idempotency guide](/api-reference/idempotency) for details.
  </Card>
</CardGroup>
